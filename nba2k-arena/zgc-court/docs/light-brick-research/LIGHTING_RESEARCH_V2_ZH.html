1. 结论与下一步决策

继续研究原生实时灯光有明确价值。当前第一优先级是让一个保留原生身份与配套引用的灯，在最终游戏文件里可控地生效，同时证明它没有被构建流程删掉。

本轮比第一轮多确定了三个直接影响实验可靠性的事项：

  1. N16 会主动删除旧测试前缀下的灯。 strip_scene() 清理 zgc_n4: 至当前夜景前缀以及旧诊断前缀，覆盖 Light 等五类内容；patch_scene_current.py 在重新生成夜景之前调用它。把旧诊断灯加回去再跑现有补丁，会在输出之前丢失该灯。S1 S2
  2. 当前补丁明确假定探针 USE_RELIGHTING == 0。 随手把该值改为 1，会与 _probe_gain() 的断言冲突。它不能被当成已经证实的实时灯开关；引擎端实际含义仍需独立验证。S3
  3. 上一轮只读取证工具会忽略长度小于 5 的名称引用。 本轮用 B0 合成样本重现了漏提取，并修复为跟随非空、唯一精确名称引用；歧义继续明确报告。旧工具可能漏掉短名称引用，但本轮尚未证明实际球场使用此类短引用。

这些发现不构成最初 N4 失败的完整根因。尤其 N16 清理规则属于后续流程，不能倒推为早期 N4 的失败原因。

推荐推进顺序：

确认最终文件保留实验灯与控制变量
  → 验证已有原生灯在其已知有效场景中可控
  → 保留身份和依赖关系，验证目标 Blacktop 的接入
  → 再研究移位、影响范围与索引更新
  → 最后独立验证新增动态阴影

不要把全部工作压在一个未经验证的命题上：LIGHT_BRICK_MAP 是否就是新灯被忽略的唯一原因，目前仍未确证。

3. 现在场景里的“灯光”实际上由哪些部分组成

3.1 灯具表面发光与泛光

_add_emitter() 使用原生路灯发光材质，给新物体复制路灯 UserData，创建与物体同名的 level.Texture，写入独立 UV7 和 Duv7。项目历史记录中，缺少同名纹理绑定的诊断盒不亮，完整绑定的盒子发光并带泛光。S3 S4

这套绑定解决的是发光表面如何被该材质路径正确解释。 它与新增一个可投影的 Light 对象是不同的接口。48 字节 UserData 的每个字段还没有在本报告中解码；照抄这段数据的成功经验，也不能自动推广到灯的注册。

3.2 球员与地面的亮区来自预计算探针的修改

当前 _probe_gain() 从已有探针读入 SH 系数，按高斯区域施加增益、颜色变化和指向光源的 L1 分量。源代码对数据规定以下读取契约：S3

LIGHT_PROBE_GRID_DATA.Attribute:
    VERSION = 4
    USE_RELIGHTING = 0

PROBE_DATA 描述:
    Dimension = BYTEADDRESSBUFFER
    Format = R32G32B32A32_FLOAT
    Width = 7
    Height = count
    原始字节数 = count × 112

每条记录:
    28 个 little-endian float32
    [0:3] 为第一组 RGB；第 4 个 float（索引 3）要求为零
    后续 24 个 float 被按 8 组 RGB 处理

这里的 112 字节来自 7 × 4 × 4，属于探针记录。它没有建立 LIGHT_BRICK_MAP 的步长、字节序或字段含义。

探针位置使用 PROBE_POSITIONS + GRID_ORIGIN；单元引用使用每单元 8 个 uint32 索引，以及一个字节的状态位。源码据此筛出实际被引用的探针。报告记录的 L1 轴顺序 Y, Z, X 来自项目 N14 游戏诊断；本轮没有重新校准引擎的 SH 符号、归一化或卷积约定。S3 S4

3.3 当前照明为什么容易“亮了，但没有真实灯的空间感”

下面是从代码得到的直接分析，范围限于当前自制探针增益算法：

  • 发光强度与照射强度分开调。 发光表面由 EMITTERS 控制，附近亮区由 PROBE_GAIN_REGIONS / WARM_GAIN_REGIONS 控制；两者没有在这段实现中建立统一的能量换算。调亮字母本身，不会按同一物理模型自动增加门口的照度。S3 S6
  • 亮区继承 donor 的原始探针能量。 代码使用 changed[selected] *= multiplier[selected]，新增 L1 的 added_l0 也乘以原始 data[:, channel]。因此增益与旧探针的能量和颜色耦合；某通道原值为零时，该写法不会凭增益创造该通道的 L0 能量。这是算法性质；当前 donor 每条记录的实际数值还需要另行读取。S3
  • 新增几何的遮挡没有被这段算法重新计算。 高斯权重使用位置距离和高度淡出，没有对 Chili’s 墙面、围栏或门洞做光线可见性求解；报告也明确保持原有可见性数据不变。这解释了为什么继续堆高斯增益无法自动获得新墙体的准确遮光边界。游戏已有的其他阴影效果仍可能存在。S3 S4

所以，玩家走到 A 字牌旁变亮，可以由既有探针方案产生。判断新增实时灯是否成功，必须固定探针与发光材质，只改变候选灯，并观察与该变化一致的直接受光响应。

3.4 新增直接光与新增动态阴影需分别验收

一盏灯的直接受光、镜面响应、阴影资源建立、动态物体参与遮挡，是不同的验证项。N4 的 SPOT 已包含 VC_CastsShadows、VC_IgnoreDynamicCasters 等字段，但仅有这些字段无法证明运行时成功分配了阴影资源。S7

最终阴影验收应让球员或其他可控动态遮挡物跨过候选灯光路，观察接收面上与候选灯位置对应的阴影变化。仅凭脚底既有阴影、接触暗角、球员身上的明暗变化或场景泛光，都不足以单独确证新灯的动态投影。

4.2 对下一轮实验的实际影响

若协作者沿用旧 N4 脚本加灯，随后运行当前完整夜景补丁，最终 IFF 可以加载正常、夜景也正常，但候选灯已经消失。这个现象很容易被误判为“游戏忽略新增灯”。

需要增加一道打包后检查：从真正要交给游戏的 IFF 再读取 SCNE，确认候选灯及其配套引用仍在。 检查源 Python 字典、编辑中的 SCNE 或 Blender 灯对象都不够。

建议独立研究入口在生产夜景清理完成之后加入诊断；新增研究对象可使用与旧前缀无交集的名称，例如 zgc_lbdiag_v1:。该名称只为避免当前清理规则，完全不代表游戏认可此名称。复用已有原生灯槽时，应首先保留原生名称和原生关联，不能为了命名整齐先改掉身份。

本报告随附 6 项合成流程测试，覆盖旧前缀清理、独立名称保留、五类内容清理、探针描述恢复、共享资源保护以及 relighting 断言。测试使用源码摘录和简化资源遍历桩，未运行完整项目封装或游戏。

5. N4 的注册问题：哪些已知，哪些仍是假说

N4 新灯已有 vc_ingame_light: 1、VC_IsActive: 1，全部设为 VC_IsMovable: 0。SPOT 也写了方向、锥角、阴影属性和世界位置。再次启用同样的布尔字段、再次加大强度，都没有解决新增的证据缺口。S7

值得核对的具体关联是：

Light 字典键：  zgc_n4:flood_upper
VC_LocatorName：zgc_n4_flood_upper

N4 的这个补丁没有为候选灯显式创建同名定位节点。但以下两件事都尚未被证明：定位节点是否必须存在；灯键与 VC_LocatorName 是否应该相同。原生样本可能使用完全不同的组织规则，所以不要直接统一改名。S7

研究假说 当前依据 最有区分力的检查
灯根本没进入最终产物 N16 有明确清理行为 最终 IFF 提取，确认条目、属性与引用
场景入口、模式或运行时覆盖不同 当前测试目标是 Blacktop；原生 donor 来自另一场景 在样本已经有效的同一入口先控制已有灯，再测试目标入口

这些解释可以同时存在。表未更新是有价值的候选，尚不具备排他性。

6. 对 LIGHT_BRICK_MAP 的研究需要怎样升级

6.1 先确认谁读取这张表

第一轮重点是“拿样本做差分”。第二轮应增加反查读表代码：从真实 SCNE 的绑定、关联 .fx / 脚本 / shader 定位消费端，检查表是直接传给着色器，还是经过 CPU 解码或运行时重新生成后才使用。

这一步可以避免两个误区：把探针重照明映射当成局部直接光索引；把 GPU 运行时展开后的布局直接当成磁盘上的压缩布局。

若实际资源是 HLSL ByteAddressBuffer，微软定义只说明它按字节寻址，并支持不同宽度的 Load；资源名字或 Format 标签没有替项目定义业务字段。即使某份描述列出了 RGBA 格式，也不能据此推定每项一定是四个 float。E1

对于可识别、工具支持的已编译 HLSL，微软提供 D3DDisassemble 取得指令文本。这是调查读取偏移、位运算和边界检查的一条工具路线；它不承诺处理所有 2K 私有 shader 容器，也不代表本轮已经反汇编了游戏 shader。E2

若需要运行时图形捕获，应仅在允许捕获的本地测试环境中进行；捕获被环境阻止时就停止该路线，不修改反作弊。追查所有相关 draw / dispatch 的读写链，不能只检查球员材质的一个像素着色器。报告不预设 2K26 的具体渲染架构。

6.2 成对样本要记录什么

优先顺序是：已有可用原生灯的同版本样本；该样本的单灯参数对照；最后才是新增灯或空间重分配样本。网上“更好看的 Lighting Mod”可以提供线索，但要通过文件差分区分其改变了灯参数、探针、材质、后期，还是新增了注册数据。

每份证据至少保存：原始 SCNE、灯条目的顺序和完整值、真实资源描述、实际引用名、包内／显式缓存解析情况、原始字节、gzip 魔数识别结果、加载入口和游戏版本。未解析引用、重复名称和预算跳过要分开列出。

目前已有的室内 donor 路径为：

nba2k-arena/donor/original/arena_020_int_original.iff

依赖清单／LFS 指针记载它为 45,028,875 字节；项目交接记录写有 18 个 SPOT 和 4 个 AREA。本轮没有重新数到这些原始灯，也未证明该文件包内包含全部外部照明资源。S8 S9

Git LFS 指针与真实文件分离是正常机制，拿到指针不能当作读到了 IFF。此次真实 LFS 内容下载未成功，因此本报告没有具体的多灯表十六进制布局可展示。E3

6.3 索引格式候选应当如何被证伪

以下列出候选编码族，尚未建立实际格式定义：

候选 可以检查的可重复性质 不能据此直接断言的内容
定长位图 新增单个成员时少量 bit 改变；大小与候选容量有可解释关系 bit 编号未必等于 SCNE 灯顺序
固定槽位索引 多块相同步长、可解释空槽、值域受稳定约束 0 可能既是有效 ID，也可能是空值
offset/count 加索引池 列表边界始终落在资源内，偏移和长度共同解释差分 相邻两个整数碰巧合理不等于格式成立
空间多级映射 位置变化对应局部块变化，可解释范围／层级 名称中的 brick 不能证明具体网格轴序或 Morton 编码
运行时派生数据 磁盘表与 GPU 缓冲有稳定转换关系 GPU 值域不能直接用来覆盖磁盘文件

特别要保留灯条目的原始顺序。实际索引可能针对全部声明灯、仅局部灯、仅活动灯、按类型分组后的灯或另一层资源 ID。Sun 是否占索引位也未知。把灯名排序后重新输出，会给这种研究引入额外变量。

成对字节比较也要区分覆盖式修改与插入式修改：前端插入一个记录可能让后面所有偏移变化，普通逐字节 diff 会夸大改动范围。任何布局假说都应在另一份未用于推导的样本上复核，并先完成无修改往返与未知字节保留，再进入写回实验。

7. 最小实验安排：每一步都有停止条件

以下是顺序执行的实验矩阵，不要求一次交给用户所有候选。先在离线检查中排除无效文件，每轮只交一个候选与明确观察目标；确需对照时一起说明原版基线。

阶段 只改变什么 保持什么 通过标准／失败后的去向
P0 最终文件核验 不进游戏，仅检查交付 IFF 所有生产内容 候选灯、顺序、定位引用、资源条目确实仍在；不在则先修研究入口
P1 控制一个已有灯 现有灯的颜色；必要时强度零／非零另做一对 名称、数量、类型、位置、表、探针、材质、后期 在该样本已知有效入口出现对应变化；无变化先查入口／覆盖／绑定
P2 验证目标接入 将保留身份的原生灯及实际必要依赖接入研究副本 当前场地、玩法锚点、篮架与材质 Blacktop 中直接受光按候选灯变化；不要整份覆盖 donor SCNE
P3 检查可移动路径 单灯 VC_IsMovable: 0 → 1 其他灯参数和表 若有可重复差异再追运行时登记；失败不能证明引擎不支持
P4 空间与范围 位置或范围其中一项 灯身份、其他参数 比较旧覆盖区与新覆盖区；异常截断是索引范围假说的线索
P5 新增成员 单个新灯及已理解的登记数据 已通过的灯与控制区域 原有灯保持正确，新灯可控；检查编号、容量和溢出
P6 动态投影 在已通过直接受光的灯下移动遮挡物 探针、相机、后期 接收面出现与该灯对应的动态阴影；单独记录比赛与回放

P2 有一项必须前置核对：原生灯原有影响范围是否覆盖目标测试位置。 为保留表而完全不移动灯，可能让它照在球场之外；一口气把灯搬到 Chili’s 门口，又会把空间映射问题混入首次接入验证。先查原有坐标与覆盖范围，再选测试区域。

项目自制场景有 180° 对象变换，代码记录模型空间 (x,y,z) 显示为世界 (-x,y,-z)。诊断中所有灯位置、光锥方向、AREA 端点、locator 及网格范围都应注明坐标空间，避免重复旋转或遗漏旋转。保留原生样本契约，再验证每个字段的空间含义。S6 S7

8. 新增最终文件检查门槛

后续研究候选在交给游戏前应逐项通过：

产物身份： 从实际交付路径读取，不从缓存的中间 SCNE 推断；记录已有版本信息和输出字节数，不触发整包重新哈希。

实验内容： 候选灯存在且唯一；关键参数等于计划值；灯序列／原有条目数量变化符合实验；同名或短名称引用无未解释歧义。研究名前缀不受当前 cleanup 影响，复用的原生灯保留其原生身份。

验收状态： 离线解析、最终 IFF 存在性检查、直接受光游戏结果和动态阴影游戏结果分别记载；没有对应游戏测试就保持未验证。

10. 如何在索引研究期间继续提升成品

生产夜景与原生灯实验应保持分离。保留已经工作的灯牌发光路径，避免为了测试实时灯再次更换所有材质、地面或后期。现有高斯探针光可承担环境氛围，但精细门洞投光、围栏遮挡和新增玩家投影，应归入各自需要验证的路径。

为本场景推进完整品质，可按以下职责分工：

工作 交付内容 不应宣称的结果
原生灯接入 一个可控灯槽、完整引用及单变量受光测试 仅有发光表面就叫实时灯成功
索引反解 样本、消费端证据、字段假说、往返测试与独立样本验证 只有合理整数统计就叫格式已破解
静态照明 新几何对应的遮挡与烘焙效果、材质接收路径验证 烘焙结果能自动产生新增动态投影
游戏验收 最终文件、入口、相机、设置及成对结果记录 网页预览或 CRC 通过就算游戏成功
