# NBA 2K26 中关村大融城：实时局部灯与动态阴影研究

日期：2026-10-06。对象：`arena_700_int.iff` 夜景；分支 `大融城OG-Snippy-snoopy-Dingus-court`。研究范围仅限用户随附资料和项目代码的读取。本轮没有访问游戏安装目录，没有写回 GitHub，没有运行游戏，也没有输出完整 IFF。

## 0. 结论与交付边界

**【数据/代码】本轮完成了 9,643,472 字节缓冲的可复现结构分析、两个完整参照 SCNE 的读取、N4 属性集合比对，以及一个只输出 SCNE 替换件和必要新增成员的诊断生成器。26 项离线测试通过。当前夜景包的完整 `level.SCNE` 没有包含在附件中，因此交付物没有伪造可直接安装的完整场景；生成器需读取项目工作区中的当前夜景 IFF 副本，或完整 SCNE 导出件。**[D1–D7]

**【推断】实时局部灯仍值得测试，但目前没有证据保证 Blacktop 模式加载这些灯、为它们分配阴影图，或正确消费重新指向的 brick 数据。官方 020 的静态定义证明引擎资产格式存在 SPOT、AREA 和对应阴影参数；这些定义无法独立证明当前 Blacktop 的运行路径和预算。**[D3]

**【数据/代码】缓冲的结构已收敛到：64 个零 word、两个值为 1 的 word、1,205,400 个八字节记录，以及八字节尾部。840 个特殊记录严格组成一个规则长方体；按与探针原点一致的坐标解释，中圈在其内部。**[D1]

**【推断】尚未建立完整语义解码器：同一份数据同时符合“16 位元素偏移”和“32 位元素偏移加低位标志”两种解释。位图候选段只出现 `1`，无法据此找出一串被删除的历史灯编号。**[D1]

**【代码/假说】提供五种单灯诊断：追加、仅资源别名控制、显式授权的 word64 单字节实验、前置顺序实验、movable 实验。其中 `word64-2` 只把 byte 256 从 `01` 改为 `02`；它是一项受控扰动，不能标成“已正确重建 LIGHT_BRICK_MAP”。前置方案不重建任何索引，但也不能标成“恢复了已知历史编号”。**[D6]

### 证据标签

- **【数据/代码】**：附件字节、原始 SCNE、源码或离线程序直接读取/计算出的结果。引用用户游戏观察时另标“用户已验证”，本轮未复测。
- **【推断】**：受到数值、空间关系或反例支持，尚缺消费端或游戏验证。
- **【假说】**：为了让下一次测试有区分能力而提出；不能作为资产格式事实。
- **【旁证】**：仅见于第三方洛克公园 mod，不能据此认定游戏效果正确。

## 2. LIGHT_BRICK_MAP：已确定的字节结构

### 2.1 原始字节与完整长度核对

**【数据】对象为 `ours/light_brick_map_grid_runtime_data.4c92381972a58bee.bin`。SHA-256：**[D1]

```text
331ee7990a7da5e63a86c8c7b108b7d10d330dd83e4bb227bafc70d1195eb535

文件长度             = 9,643,472 bytes
Texture.PixelDataSize = 9,643,472
Texture.Height        = 2,410,868
Height × 4            = 9,643,472
```

**【数据】按 little-endian uint32 检查，全部 word 只有以下五种值。这里列出的是存储数值，没有把它们命名为灯 ID。**[D1]

|uint32 值|十六进制|出现次数|
|---:|---:|---:|
|0|`0x00000000`|1,205,465|
|1|`0x00000001`|2|
|262,144|`0x00040000`|1|
|4,821,732|`0x004992E4`|1,204,560|
|4,821,733|`0x004992E5`|840|

**【数据/推断】用标记给出的数值作为候选 word 边界，能得到下表并完全覆盖文件，无剩余字节。区段内容与长度直接可验证；“位图”“目录”等区段名称仍为候选解释。**[D1,D2]

|字节区间，左闭右开|word 区间|直接读到的内容|候选用途及限制|
|---|---|---|---|
|`[0,256)`|`[0,64)`|64 个零|可能是一个含 4³ 元素的细格块；零的含义未知。|
|`[256,260)`|`[64,65)`|`1`|位图行候选。尚未确认它是否描述当前运行时灯集合。|
|`[260,264)`|`[65,66)`|`1`|伴随行候选。没有证据把它命名为 popcount、灯数或行大小。|
|`[264,9643464)`|`[66,2410866)`|1,205,400 个 `[low32,high32]`；high32 全为零|每个粗格对应一个八字节记录的解释高度自洽。两个字段的语义未定。|
|`[9643464,9643472)`|`[2410866,2410868)`|u32=`[0x00040000,0]`；u16=`[0,4,0,0]`|目录引用的尾部候选。`4` 的类型和含义未知。|

**【代码】分析器按这些区段拆开后重新拼接，SHA-256 与输入完全一致。这是“保留不透明区段的结构重组”，不能写成已完成语义解码再编码。**[D1,D6]

### 2.2 两种都成立的寻址解释

**【假说 A：16 位元素偏移】**将记录的 low32 乘 2：

```text
4,821,732 × 2 = 9,643,464 -> 读到 uint16 0
4,821,733 × 2 = 9,643,466 -> 读到 uint16 4
```

**【假说 B：带低位标志的 32 位元素偏移】**先右移 1，再乘 4：

```text
(4,821,732 >> 1) × 4 = 9,643,464，低位标志 0
(4,821,733 >> 1) × 4 = 9,643,464，低位标志 1
共同目标 uint32 = 0x00040000
```

**【数据】对全部 1,205,400 个记录，两种解释的寻址都在界内，且全部命中尾部。**[D1]

**【推断】仅用“指针没有越界”无法选择 A 或 B。也还可能存在其他打包方式。因此当前不能确认每个细格最终存灯位掩码、位图行索引、可变长灯列表、压缩块句柄，或它们的组合；粗格目录很可能承担间接访问，但路径尚未闭环。**[D1]

**【数据】若把 word64 当成 32 位灯集合，它的唯一置位位置为 bit0。这个条件结论不等于“引擎实际只引用灯 0”。正式运行时编号范围仍未知；尾部 `4` 不构成灯编号 4 的证据。**[D1]

## 3. 格子位置：中圈是否处于被引用区域

**【数据】少数记录 `[0x004992E5,0]` 一共 840 个。采用 `i=x+210×(y+35×z)`，其坐标严格填满：**[D1]

```text
x = 99..110   共 12
 y =  5..9    共  5
 z = 67..80   共 14
12 × 5 × 14 = 840
线性索引首尾：493599 .. 590000
```

**【数据】检查六种简单的轴快慢排列，只有 X 最快、Y 次之、Z 最慢的排列把这 840 个记录解释成无洞的包围盒。其他布局、Morton 编码等未因这项检查被数学排除；当前简单线性布局证据最强。**[D1]

**【推断】令 DATA 维度 D、cell size h、origin offset t，以下坐标公式与现有数据一致：**[D1,D2]

```text
origin = (t.x - D.x*h/2, t.y, t.z - D.z*h/2)
       = (-42000, -2800, -29600) cm
fine   = floor((world_position - origin) / 100)
brick  = fine // 4
linear = brick.x + 210*(brick.y + 35*brick.z)
```

**【数据】上述 origin 与 `LIGHT_PROBE_GRID_DATA.GRID_ORIGIN` 完全相等。按该公式，中圈 world=(0,0,0) 对应 fine=(420,28,296)、brick=(105,7,74)、目录索引 545475、word 起点 1091016，读到特殊记录 `[4821733,0]`。**[D1]

**【推断】840 个特殊粗格的世界包围盒为 X `[-2400,2400)`、Y `[-800,1200)`、Z `[-2800,2800)` cm。它覆盖当前中圈及较大的周边空间。不过，“特殊记录范围”与“有光的范围”尚未等同，粗格中的 64 个细格是否共享有效集合也需要解码确认。**[D1]

**【假说】中圈单灯是合适的首个实验位置：不用移动网格、不用创建新粗格，也不必先解决新光源包围盒如何编码。这个选择减少变量，不能替代对最终灯 ID 的验证。**

## 4. 灯编号、名字与“恢复旧灯”假说

### 4.1 官方 020 给出的反例

**【数据】完整官方 Light 字典顺序为：Sun（序号 0，inactive），随后四个 AREA，最后 18 个 SPOT。四个 AREA 的短名字顺序为 `court_line_light_0, 2, 1, 3`，明显不等于名称自然排序。全部 22 盏局部灯 `VC_IsActive=1`。完整逐项顺序已输出，不依赖截断片段。**[D3]

**【数据】18 个官方 SPOT 的 `VC_PresentationLightId` 全是 0，AREA 没有这个属性。**[D3]

**【推断】`VC_PresentationLightId` 单独无法作为这 18 盏灯各自唯一的编号。这不排除该字段还承担分组、presentation 状态或其他作用；这些作用本轮未知。**

**【数据/推断】如果假定 bitmask 是“每盏当前局部灯一个 bit、按 32-bit 紧密排列”，22 盏应只需 `ceil(22/32)=1` 个 word；官方描述符给 2。因此“MAXWORDS 就是当前 Light 数量除以 32 向上取整”这一简单规则不能由本样本成立。预留编号、多个灯类别、编译历史、AREA 内部分解等均只能列为候选解释，未选择其中任何一个。**[D2,D3]

### 4.2 能否决定按顺序、名称哈希或 Presentation ID

|候选映射|本轮判断|可区分的后续证据|
|---|---|---|
|按 Light 原文顺序，包含 Sun|尚可测试；当前没有 runtime 数组可以核对。|`append` 与 `prepend` 且原 grid 不动的单灯实验。|
|只按 active/local 灯顺序|尚可测试；官方 Sun inactive、AREA/SPOT 混合，不能拿字典序号直接充当 bit。|官方 runtime buffer 加实际运行时灯常量数组。|
|按名称/名称哈希|无已解出的哈希到编号表，不能证实或排除。|相同灯参数和顺序，仅变名称的独立实验；或加载器/消费端映射。|
|按 `VC_PresentationLightId` 单独区分每灯|受官方 18 个相同值的直接反例否定。|仍可研究它的其他作用，不在本轮给灯任意编号。|

**【数据】对两份完整 donor SCNE，逐个 locator 字符串检索 Light 之外的所有键和字符串值，命中均为零。范围包含 Object、Model、Material、Effect 等，不局限于 subset。**[D3]

**【推断】当前没有证据要求给每个 SPOT 再新增一个同名 Object。locator 可能供外部资源或运行时使用，这份静态检索不能排除外部引用。诊断保留该字段，并使用 `zgc_rtl:center_spot`，不制造未经证实的 Object 绑定。**

### 4.3 原始 700 曾有很多灯、后来删除的假说

**【数据】当前附件只给 ours 的 Sun 和继承 grid，没有给“未经项目修改的原始 arena_700_int 的完整 Light 字典及顺序”。word64=1 也没有提供一组可确认的 1..N 编号。**[D1,D8]

**【代码】附件当前 `night_lighting.apply_night` 会断言 Light 列表恰好为 `['Sun']`。它期望输入本来只有 Sun；这段函数本身不能证明删过很多原生灯。旧流程、其他工具或更早版本是否删除过，需要原始 700 和历史基线比较。**[D5]

**【推断】“按原编号放回若干灯即可复活”目前缺少两条链路：历史灯身份/顺序，以及 grid 到 runtime 灯编号的映射。不能把尾部数值 4 当作第四盏灯，再凭名字或 Presentation ID 重建那盏灯。**

**【假说/代码】提供 `prepend`：把唯一新 SPOT 放在 Sun 之前，其余原始定义和 grid 一字节不改。只有在原始 grid 的有效集合最终引用槽位 0、引擎按该顺序构造数组且不剔除/重排的条件下，它才可能使新灯进入集合。成功将支持某种顺序依赖；失败无法单独否定所有旧编号恢复路线。此方案是“零重建的槽位假说测试”，没有冒充真正的历史还原。**[D6]

## 5. 完整原生灯写法与 N4 比较

### 5.1 N4 已经具备官方属性集合

## 6. CompressionMethod 33 与资源加载

**【数据】附件 raw `.bin` 开头至少 256 字节为零，没有 gzip 的 `1f 8b` 文件头；完整长度等于 Texture 声明长度，多个分区/指针候选无需解压即可自洽。RFC 1952 给出的 gzip 固定头字节用于这一有限判断。[D1；外部 R1]**

**【代码】附件工具把 SCNE 中 `.gz` 的引用解析到同 stem 的 `.bin`，并且现有夜景流程明确使用这种别名。ZIP/IFF 成员自身的压缩，与 Texture 的 `CompressionMethod` 是两个不同层次。**[D5]

**【推断】对这份明确提供的 `.bin` 应直接读取 raw 字节；不能因为引用名以 `.gz` 结尾，就再套一次 gzip 或 Oodle 解压。另一方面，本样本不能给引擎内部枚举 33 命名；不能推广为“所有 33 都不压缩”或“33=gzip”。需要资源加载器/格式枚举或同类型加载追踪才能回答其精确定义。**

**【假说/代码】资源引用诊断采用现有 canonical Texture 条目 `LIGHT_BRICK_MAP_GRID_RUNTIME_DATA`，只将其 Binary 改到 `zgc_rtl:light_brick_diag.gz`，新增 raw IFF 成员 `zgc_rtl:light_brick_diag.bin`；所有大小、格式、CompressionMethod、标记保留。canonical 键已经存在，不能为了前缀要求擅自改名，否则可能断开引擎约定绑定。**[D6]

**【推断】自定义成员名能否走实际游戏的资源解析同样需要测试。为避免把“新名字加载失败”误当成“位图解释错误”，`alias` 与 `word64-2` 使用完全相同的 SCNE、成员名字和长度，仅比较一个 raw 字节。即使二者都失败，资源别名是否被实际消费仍未获证明；需要下一份数据或消费端观察。**

## 7. 怎样生成正确的新索引表

**【结论/推断】空间覆盖计算可以设计并实现；符合游戏真实消费格式的最终字节编码还没有足够信息。当前交付不包含伪装成通用编译器的代码，不把未确认的尾部 `4`、word65、O2 高位写成自创定义。**

### 7.1 待格式闭环后的算法

**【设计/假说】以下流程描述需要满足的语义，不给未知二进制字段强行命名：**

```text
输入：已验证的 runtime 灯数组与稳定编号、SPOT 位置/方向/范围、网格参数

1. 取得 world -> fine cell -> brick 的实际变换，确认边界与轴序。
2. 为每盏灯计算影响体：有限锥体及引擎真实衰减范围。
3. 遍历影响体包围盒覆盖的候选细格：
   做保守的 cell-AABB 与影响体相交测试；边界有疑义时宁多纳入，避免漏光。
4. 得到各细格的灯集合 S(cell)，保留已存在且应保留的 Sun/局部灯成员。
5. 验证编号空间、不同灯类别、bit 顺序及是否有保留 ID。
6. 按已确认格式去重集合行、去重 4^3 细格块，编码真实的目录和尾部。
7. 按实际 capacity 语义处理溢出；未知时拒绝生成，不能默默截掉第 5 盏灯。
8. 计算真实 offsets、字节长度、Height、维度及必要构建标记。
9. 校验每个引用界内、每个灯编号有效、所有包围盒外/内样点符合预期。
10. 对至少一个非平凡官方样本完成语义 decode -> encode，
    再执行移动一盏灯、重排两盏不同颜色灯的独立游戏对照。
```

**【设计/推断】2–4 盏灯的几何覆盖问题很小，首先确定当前网格是否覆盖灯具及受光表面；能复用网格就不扩大。真正缺口为稳定灯编号、细格集合的压缩/间接表示、raw/资源布局和运行时消费确认。仅把 GRID_DIMENSIONS 改为 `[4,4,4]` 或填满 `0xFFFFFFFF` 没有格式依据，可能越界，不能作为可用重建方案。**

**【假说】`word64-2` 是缩小后的单集合实验：如果 word64 是集合位图、word65 在单置位情况下可保持 1、且新增灯对应 bit1，那么 `1→2` 可能把同一覆盖区域从候选槽位0切换到候选槽位1。这里每个“如果”都尚未验证。不能据此修改别的位、灯数、word65 或尾部。**

**【风险】若 word64 实际是计数、标志或索引，此变更可能无效、改变错误资源，甚至导致崩溃；同时它可能改变 Sun 的集合关系，尽管 Sun 的定义完全未改。脚本要求 `--ack-unverified-word64`，只接受本轮 grid 的精确 SHA，不能用于其他场馆或生产构建。**[D6]

## 9. 最小游戏内诊断与观察标准

### 9.1 生成与封装位置

**【代码】基础诊断新增且仅新增一盏 `zgc_rtl:center_spot`，world=(0,800,0)，向下，冷白，高强度，投影开启。没有灯具模型、没有发光贴图、没有假地面光斑、没有新探针。各变体均从同一个干净的最终夜景工作区副本生成。**[D6]

**【代码】先完成现有 night 构建，再生成本诊断并交给最后的封装步骤。`night_lighting.py` 当前的 Sun-only 断言会拒绝多灯输入；把诊断放在它之前会失败。不要删掉生产断言，不要在诊断之后再跑会重写场景/清理旧灯的流程。最终封装后运行本工具的 `verify`，检查灯条目与顺序确实留在最终 SCNE 中。**[D5,D6]

|变体|相对干净基线的变更|验证目的；解释边界|
|---|---|---|
|A：`append`|Sun 后追加一盏；grid 与描述符均不改|注册/当前索引是否已足够；可作为完整写法基线。|
|A′：`alias`|同 A；canonical grid Texture 改 Binary 引用；新增原 grid 的逐字节副本|与 B 构成相同资源名和 SCNE 的控制组。A 与 A′有差异时先调查资源解析。|
|B：`word64-2`|与 A′ 的 SCNE 完全相同；新增 buffer 的 byte256 由01变02|仅测试一个未知 word 的因果作用；需要显式授权；无格式正确性保证。|

### 9.2 什么算成功

**【设计】最小目标的成功需要同时出现三项，且能通过单变量对照消失/改变：**

1. 中圈附近出现新的局部冷白照明区域，边界与向下聚光灯相符；`--intensity 0` 对照下新照明消失。
2. 球员走入区域时，身体/衣物的直接受光明显变化，走出后回到基线。
3. 地面出现随球员位置/动作更新、几何关系与顶上新灯一致的投影；保留相同强度、仅用 `--casts-shadows 0` 时该新增影子消失，而直接光仍在。

**【推断】只出现亮斑属于“静态表面受光通过”；亮斑加球员亮属于“直接光基本通过”；必须确认第3项，才能回答动态阴影目标。Sun 的既有影子、烘焙遮蔽、脚底接触阴影或曝光变化都不足以单独证明新灯投影。**

### 9.3 失败时先改哪一个变量

|游戏/封装结果|可以下的结论|下一步，仅改变一类变量|
|---|---|---|

**【设计】每次记录 build/manifest SHA、变体、机位、球员路径、是否亮地面/球员/投影，并保存同机位短视频。验收表模板见 [GAME_TEST_LOG_TEMPLATE.md](GAME_TEST_LOG_TEMPLATE.md)。**

## 11. 工程保护、测试覆盖与不能声称的结果

**【代码】生成器写入范围被限制为所选工作区下的新 `docs/realtime-light-research/` 子目录，拒绝覆盖现有输出，拒绝工作区外/解析后逃逸路径，并阻止常见游戏安装路径名称。路径检查只是辅助保护；操作者仍须提供项目副本。生成器与 verify 都不调用完整 IFF 写入器。**[D6]

**【代码】payload 只有完整 `level.SCNE` 替换件，以及别名/B变体需要的一份新 grid 成员。原始 Sun 文本、全部 Object/标记、现有探针描述符、Material/Model/Effect 源文本保留；没有 PostEffect、探针或其他原始成员的替换。新灯/locator/新资源名均以 `zgc_rtl:` 开头。磁盘 payload 文件使用 `members/0000.bin`，冒号只放在 manifest 的 archive_name，避免 Windows 路径/ADS 解释问题。**[D6,D7]

**【代码】IFF 输入模式记录并复核 `PostEffect.FxTweakables` 的 SHA-256；记录其他未改成员的 CRC/长度，verify 检查这些成员和最终成员集合。CRC/长度检查提供封装回读保障，不能表述为对全部 1.7 GB 数据做了密码学逐字节证明。`--scene` 输入模式没有提供完整 archive，manifest 会明确缺少 PostEffect/成员清单覆盖；需封装者另行验证。**[D6]

**【代码】26 项测试包含真实 grid 长度/指纹、目录算术、双寻址歧义、840格空间关系、结构重组、越界/截断检测，及合成场景上的文本保留、参数单变量、别名对照、一字节修改、拒绝非基线、路径约束、manifest、封装与 PostEffect 异常检出。命令行 smoke 测试另有日志。全部仅为离线软件验证。**[D7]

**【结论】本轮没有得到一个经过游戏验证的通用 LIGHT_BRICK_MAP 编译器，也没有证明 Blacktop 可同时投射 2–4 盏局部灯的影子。已经获得的可行动结果是：N4 不缺官方那组属性；当前缓冲的目录与中圈范围可定位；Presentation ID 不能独自编号；原灯恢复需要原始700；下一轮实验可用一次一变量、仅一盏灯、受保护数据不动的 payload 进行。**
